# baseline — วัดว่ามาตรฐานลดโทเคน/เวลาต่องานจริงไหม (R1)

> เป้าหมาย: เปลี่ยนตัวเลขที่มาจาก "การให้เหตุผล" ให้เป็นตัวเลขที่ "วัดแล้ว"
> นี่คือคำถามแรกสุดที่ตั้งไว้ตั้งแต่ต้น — และยังไม่เคยตอบด้วยข้อมูลจริงเลย

---

## 🔒 โปรโตคอลวัดผล — ล็อกไว้ก่อนเริ่ม ห้ามแก้กลางทาง

> เขียนหลังการวัดรอบแรกล้มเหลว เพราะไม่มีนิยาม "จบ" ตกลงกันไว้ล่วงหน้า
> รอบหนึ่งทำจนผ่าน gate อีกรอบหยุดตอนยังมี type error 30 จุด
> แล้วเอาราคาสองรอบนั้นมาเทียบกัน — ซึ่งเทียบไม่ได้

### หลักการเดียวที่ทุกอย่างตั้งอยู่บนนี้

**ผลลัพธ์ต้องเท่ากันก่อน ถึงจะเทียบราคาได้**

ถ้ารอบหนึ่งทำจบ อีกรอบทิ้ง error ไว้ ราคาที่ถูกกว่าไม่มีความหมาย —
มันถูกเพราะ**ทำน้อยกว่า** ไม่ใช่เพราะ**เก่งกว่า**

### 1. นิยาม "จบ" — ตกลงก่อนเริ่ม ไม่ใช่ตัดสินทีหลัง

รอบหนึ่งนับว่า **จบ** เมื่อผ่านทั้งสองข้อ:

| # | เกณฑ์ | ตรวจด้วย |
|---|---|---|
| 1 | `./gate.sh --full` เขียว | tsc + lint ratchet + build + render smoke ผ่านหมด |
| 2 | ฟีเจอร์โผล่จริง | เช็คสตริงที่ตกลงไว้ก่อนเริ่ม เช่น `grep -r "พักงานชั่วคราว" src/` |

เขียนเกณฑ์ข้อ 2 ลงในตารางผล **ก่อน**เปิดแชตวัด

### 2. ⚠️ ในโหมด `clean` — AI ตัดสินเองว่า "จบ" ไม่ได้

`gate.sh` ถูกซ่อนไปแล้ว (นั่นคือจุดประสงค์ของโหมดนี้) AI จึงไม่มีเครื่องบอกว่ายังไม่จบ
มันจะหยุดตอนที่**มันคิดว่า**เสร็จ ซึ่งไม่ใช่เกณฑ์เดียวกับอีกช่อง

→ **การตัดสิน "จบ" ต้องทำหลังจบรอบ ในแชตอื่น** ไม่ใช่ระหว่างที่ AI ทำงาน
→ ห้ามเอาคำว่า "เสร็จแล้วครับ" ของ AI มาเป็นเกณฑ์เด็ดขาด

### 3. ลูป 4 ขั้น ต่อ 1 รอบวัด

```
ขั้น 1  ตั้งค่า          bash standard/mode.sh reset   ← ล้าง tree ให้สะอาด
        เลือกโหมด        bash standard/mode.sh clean   (หรือ off / restore)
        ยืนยันสะอาด      bash standard/mode.sh status  ← ต้องไม่มีคำเตือน

ขั้น 2  เปิดแชตใหม่      ส่งคำสั่งที่ตกลงไว้ คำต่อคำ ห้ามใบ้ชื่อไฟล์ ห้ามใบ้ชื่อเครื่องมือ
        AI ทำงาน         ปล่อยจนมันหยุดเอง
        เก็บเลข          node standard/measure.mjs      ← จดไว้ก่อน ยังไม่ตัดสิน

ขั้น 3  คืนเครื่องมือ     bash standard/mode.sh restore
        ตัดสิน           ./gate.sh --full  +  เช็คเกณฑ์ข้อ 2
          เขียว → รอบนี้ "จบ"    → เลขโทเคนนับได้
          แดง   → รอบนี้ "ไม่จบ" → ทิ้งเลขราคา แต่ *จดว่าไม่จบ*

ขั้น 4  ล้าง             bash standard/mode.sh reset แล้วทำตามที่มันบอก
```

### 4. รอบที่ไม่จบ = ข้อมูล ไม่ใช่ขยะ

**อย่าทิ้งเงียบ ๆ** ถ้า `clean` ไปไม่ถึงจบบ่อย ๆ ขณะที่ ON จบทุกครั้ง —
นั่นคือผลของมาตรฐานที่**แรงกว่าเรื่องราคาอีก**

มาตรฐานไม่ได้แค่ประหยัด แต่ทำให้ **จบได้จริง**

จึงได้ตัวเลขสองตัวที่มีความหมายทั้งคู่:

| ตัวเลข | นับจาก |
|---|---|
| **ราคา** | เฉพาะรอบที่ "จบ" เท่านั้น |
| **อัตราจบ** | จบกี่ครั้ง จาก กี่ครั้งที่รัน (นับทุกรอบ) |

### 5. เผื่อเวลาไว้ — บางรอบจะถูกทิ้ง

กว่าจะได้ **3 รอบที่จบ** ต่อช่อง อาจต้องรัน **4–5 ครั้ง**

และถ้าโหมด `clean` แทบไม่เคยถึงจบเลย — **นั่นคือคำตอบในตัวมันเอง**
ไม่ต้องฝืนวัดราคาต่อ

## วิธีจดตัวเลข — `/cost` ไม่มีในเวอร์ชันนี้

Claude Code ที่ใช้อยู่มีแค่ `/usage` กับ `/context` **ไม่มี `/cost`**
(โปรโตคอลฉบับแรกอ้างคำสั่งที่ไม่มีอยู่จริง — แก้แล้ว)

| จดอะไร | เอามาจากไหน | หมายเหตุ |
|---|---|---|
| **โทเคน (หลัก)** | `/usage` → `Session (5hr) %` **ก่อน**เริ่มงาน และ **หลัง**จบงาน แล้วเอาส่วนต่าง | ใกล้ต้นทุนจริงที่สุด |
| โทเคน (รอง) | `/context` → บรรทัด **Messages** ตอนจบงาน | เป็นภาพนิ่ง ไม่นับส่วนที่ถูกตัดทิ้งกลางทาง |
| เวลา | จับเวลาเอง ตั้งแต่ส่งคำสั่งจนได้ผลที่ใช้ได้ | |
| รอบแก้ซ้ำ | นับเอง | |

⚠️ **`Session (5hr)` รวมทุกอย่างในหน้าต่าง 5 ชั่วโมงนั้น**
→ ระหว่างวัด **อย่ารันงานอื่นคู่กัน** ไม่งั้นส่วนต่างจะปนงานอื่น
→ ถ้า % หยาบเกินไป (ขยับทีละ 1%) ให้ใช้ Messages จาก `/context` เป็นตัวเทียบแทน

## ⚠️ ก่อนเทียบราคา ต้องเทียบสิ่งที่ได้ก่อน

**นี่คือกติกาที่สำคัญที่สุดในไฟล์นี้**

รอบที่ถูกกว่าอาจถูกเพราะ **ทำน้อยกว่า** ไม่ใช่เพราะเก่งกว่า

ก่อนจดตัวเลขทุกครั้ง ตอบสามข้อนี้:

1. **แก้กี่ไฟล์** — `git status --porcelain | wc -l`
2. **ผลลัพธ์ใช้งานได้เท่ากันไหม** — เปิดเว็บดูจริง ไม่ใช่เชื่อคำอธิบายของ AI
3. **ผ่าน gate ทั้งคู่ไหม** — ถ้ารอบหนึ่งไม่ได้ตรวจเลย แปลว่ายังไม่รู้ว่ามันใช้ได้จริงหรือเปล่า

**ถ้าสามข้อนี้ไม่เท่ากัน ตัวเลขโทเคนเทียบไม่ได้** — จดไว้ในช่องหมายเหตุ อย่าเพิ่งสรุป

## กติกา — ผิดข้อเดียวตัวเลขใช้ไม่ได้

1. **1 เซสชัน = 1 งาน** จดตัวเลขตามวิธีข้างบน
2. **เซสชันใหม่ทุกงาน** ไม่งั้นงานหลัง ๆ ถูกเพราะ AI จำโครงได้ ไม่ใช่เพราะมาตรฐาน
3. **เลือกงาน "ก่อน" กับ "หลัง" ให้ชนิดและขนาดใกล้กัน**
4. **อย่างน้อย 2 งานแบบเก่า + 3 งานใช้มาตรฐาน**
5. **สลับลำดับบ้าง** งาน 1 ก่อน→หลัง · งาน 2 หลัง→ก่อน

### สลับโหมด

```bash
bash standard/mode.sh off       # ปิดมาตรฐาน = โหมด "ก่อน"
bash standard/mode.sh on        # เปิดมาตรฐาน = โหมด "หลัง"
bash standard/mode.sh status    # ดูกล่องสถานะ — เช็คก่อนเริ่มทุกงาน
bash standard/mode.sh reset     # บอกวิธีล้าง tree ให้สะอาด
```

## ⚠️ คำสั่งงานต้องเหมือนกันเป๊ะทั้งสองรอบ และห้ามพูดถึงเครื่องมือเลย

**ตัวแปรที่ต่างกันระหว่างสองรอบ ต้องมีตัวเดียว: `CLAUDE.md` มีอยู่หรือไม่**

- รอบ "ก่อน" ห้ามบอกให้ใช้ `scope.mjs` / `gate.sh` → เพราะไม่มีมาตรฐาน
- รอบ "หลัง" **ก็ห้ามบอกเหมือนกัน** → `CLAUDE.md` สั่งมันอยู่แล้ว
  ถ้าเราบอกเอง = เราทำหน้าที่ของมาตรฐานแทนมัน แล้ววัดไม่ได้อีก

### และห้ามบอกชื่อไฟล์

การ**หาว่าต้องแก้ตรงไหน** คือส่วนที่แพงที่สุด และเป็นสิ่งที่ `scope.mjs` มีไว้แก้
ถ้าโจทย์บอกไฟล์ให้แล้ว = ตัดส่วนที่จะวัดทิ้งไปตั้งแต่ต้น

| โจทย์แบบ | ผล |
|---|---|
| ชัดเกินไป (บอกไฟล์/ฟังก์ชัน) | ไม่ต้องหา → ไม่มีอะไรให้วัด |
| กำกวมเกินไป | สองรอบทำคนละอย่าง → เทียบผลลัพธ์ไม่ได้ |
| **กำกวมเรื่อง "ที่ไหน" ชัดเรื่อง "เสร็จแล้วทำอะไรได้"** | **ถูกต้อง** |

```
❌ แก้ src/app/jobs/new/page.tsx ให้เรียก addJob
❌ ทำให้หน้าสร้างงานดีขึ้น
✅ ตอนนี้หน้าสร้างงานใหม่ กรอกแล้วกดบันทึกไม่เกิดอะไรเลย ทำให้ใช้งานได้จริง
   พอสร้างเสร็จต้องเห็นงานใหม่ในรายการงาน และกดเข้าไปดูรายละเอียดได้
```



เขียนโจทย์ให้เหมือนตอนลูกค้าหรือหัวหน้าสั่งงานจริง — ไม่มีใครบอกชื่อไฟล์มาให้

⚠️ **ล้าง tree ก่อนทุกงาน:** `git checkout -- . && git clean -fd`
(`git checkout` อย่างเดียวไม่ลบไฟล์ใหม่ที่ AI สร้าง — งานรอบก่อนจะค้างมา)

⚠️ **เช็ค `status` ก่อนเริ่มงานทุกครั้ง** — ถ้าเผลอวัดผิดโหมด จะไม่มีทางรู้ย้อนหลังว่ารอบไหนผิด

- เพิ่มฟีเจอร์เล็ก

## ⚠️ ตั้งความคาดหวังให้ถูก ก่อนเห็นตัวเลข

**"ก่อน" ไม่ได้แปลว่า AI โง่** — AI สมัยนี้ค้นหาแบบเจาะจงเป็นอยู่แล้ว ไม่ได้อ่านทั้งโปรเจกต์เสมอไป

| ชนิดงาน | คาดว่าจะเห็นส่วนต่าง |
|---|---|
| งานเล็ก แตะไฟล์เดียว | **น้อย** — AI ปกติก็หาเจอเร็วอยู่แล้ว |
| **งานหลายไฟล์ / โค้ดพันกัน** | **มากสุด** — ตรงที่ "อ่านทั้งโปรเจกต์เพื่อความปลอดภัย" เปลืองที่สุด |

**และมาตรฐานมีต้นทุนของมันเอง** — `CLAUDE.md` เข้าบริบททุกครั้ง · `scope` และ `gate` กินเวลาและ output
ถ้างานเล็กพอ ต้นทุนนี้อาจมากกว่าที่ประหยัดได้
**ซึ่งจะเห็นเป็นตัวเลขติดลบ — นั่นคือข้อมูลที่มีค่า ไม่ใช่ความล้มเหลว**

## ⚠️ n = 5 บอกทิศทางได้ ไม่ใช่เลขแม่น

- **ดูผลทีละงาน ไม่ใช่ค่าเฉลี่ย** — ถ้า 4 งานลด 1 งานเพิ่ม ต้องรู้ว่างานไหนและทำไม
- **เลือกงานก่อน/หลังให้ขนาดใกล้กัน** เท่าที่ทำได้
- **"รอบแก้ซ้ำ" อาจชี้ผลชัดกว่าโทเคนดิบ** — gate จับพังเร็ว = ไม่ต้องวนแก้

### สัญญาณที่เห็น

```

```

**ทิศทางตรงข้ามกัน ขึ้นกับชนิดงาน** — ตรงกับที่เอกสารนี้ทำนายไว้ *ก่อน* วัด

**1. ผลลัพธ์ไม่เท่ากัน (ข้อใหญ่สุด)**
งานพักงานรอบปิดกฎ **ทำไม่จบ** — ทิ้งโค้ดที่คอมไพล์ไม่ผ่าน 30 จุดไว้
ส่วนรอบเปิดกฎทำจนผ่าน gate และ e2e ครบ

→ เอาราคาของ "งานที่ทำไม่เสร็จ" ไปเทียบ "งานที่เสร็จ" ตรง ๆ ไม่ได้
→ พูดให้ถูกคือ **"ปิดกฎจ่ายมากกว่า และยังไม่จบ"** ไม่ใช่ "ถูกกว่า 2.4 เท่า" เป๊ะ

**2. โหมด "ปิด" ยังไม่สะอาด**
สคริปต์ (`scope.mjs`, `gate.sh`) ยังอยู่ในโปรเจกต์ AI หาเจอเองและเรียกใช้แม้ไม่มี `CLAUDE.md`

→ สิ่งที่วัดคือ **"เปิด/ปิดกฎใน CLAUDE.md"** ไม่ใช่ "มีมาตรฐาน vs ไม่มีอะไรเลย"
→ ถ้าจะวัดอย่างหลัง ต้องซ่อนสคริปต์ด้วย

**3. n = 1 ต่อชนิดงาน**
รอบปิดกฎที่วน 249 รอบ อาจเป็นรอบซวยครั้งเดียว
ต้องวัด 2–3 รอบต่อช่องถึงจะเชื่อตัวคูณได้

### พฤติกรรมที่ต่างกัน (ข้อมูลประกอบ)

| งาน | โหมด | Read | Edit/Write | Bash |
|---|---|---|---|---|
| พักงาน | ปิดกฎ | 18 | **78** | 60 |
| พักงาน | เปิดกฎ | 29 | **33** | 26 |
| โทนสี | ปิดกฎ | 5 | 9 | 22 |
| โทนสี | เปิดกฎ | 14 | 8 | **53** |

พักงานรอบปิดกฎแก้ไฟล์ **78 ครั้ง** เทียบกับ 33 — วนแก้แล้วแก้อีก
โทนสีรอบเปิดกฎรัน bash **53 ครั้ง** เทียบกับ 22 — รัน gate/scope เพิ่มทั้งที่งานเล็ก

### สิ่งที่ต้องทำต่อถึงจะสรุปได้

- [ ] วัดเพิ่มให้ได้ 2–3 รอบต่อช่อง
- [ ] ทุกรอบต้อง**ทำจนจบ**เท่ากัน ถึงจะเทียบราคาได้
- [ ] ถ้าจะวัด "ไม่มีมาตรฐานเลย" ต้องซ่อนสคริปต์ด้วย ไม่ใช่แค่ `CLAUDE.md`
- [ ] เปิดเว็บดูจริงว่าผลลัพธ์แต่ละรอบเท่ากันไหม

## ⚠️ ข้อจำกัด — เขียนไว้ก่อนใครเอาตัวเลขไปอ้าง

- **โปรเจกต์ทดสอบไม่มีผู้ใช้จริง ไม่มีเดิมพัน**
  → วัด "โทเคน/เวลาต่องาน" (R1) ได้จริง
  → แต่วัด "ความกลัวลดลง" ไม่ได้ ซึ่งคือตัวเผาโทเคนที่ใหญ่ที่สุดตามที่วิเคราะห์ไว้
  → ตัวเลขที่ได้จึงเป็น **ขอบล่าง** ของประโยชน์จริงบนระบบที่ส่งมอบแล้ว

- **n = 5 น้อยมาก** บอกทิศทางได้ ยังไม่พอสรุปเป็นตัวเลขแม่นยำ

- **ยังไม่มีครึ่ง DB** (typed client, RLS smoke) ซึ่งประเมินว่าแก้ R2 ได้ 70–85%

- **จดรุ่นโมเดลไว้ด้วย** และต้องเหมือนกันทุกรอบ
