# baseline — วัดว่ามาตรฐานลดโทเคน/เวลาต่องานจริงไหม (R1)

> เป้าหมาย: เปลี่ยนตัวเลขที่มาจาก "การให้เหตุผล" ให้เป็นตัวเลขที่ "วัดแล้ว"
> นี่คือคำถามแรกสุดที่ตั้งไว้ตั้งแต่ต้น — และยังไม่เคยตอบด้วยข้อมูลจริงเลย

---

## กติกา — ผิดข้อเดียวตัวเลขใช้ไม่ได้

1. **1 เซสชัน = 1 งาน** จบแล้วพิมพ์ `/cost` จดทันที
2. **เซสชันใหม่ทุกงาน** ไม่งั้นงานหลัง ๆ ถูกเพราะ AI จำโครงได้ ไม่ใช่เพราะมาตรฐาน
3. **เลือกงาน "ก่อน" กับ "หลัง" ให้ชนิดใกล้กัน** พอเทียบได้
4. **อย่างน้อย 2 งานแบบเก่า + 3 งานใช้มาตรฐาน**
5. **สลับลำดับบ้าง** งาน 1 ก่อน→หลัง · งาน 2 หลัง→ก่อน (กันผลจาก cache/ความเหนื่อยของเครื่อง)

### สลับโหมด

```bash
bash standard/mode.sh before    # ปิดมาตรฐาน (สภาพเดิม = ไม่มี CLAUDE.md เลย)
bash standard/mode.sh after     # เปิดมาตรฐาน
bash standard/mode.sh status    # ตรวจว่าตอนนี้อยู่โหมดไหน  ← เช็คก่อนเริ่มทุกงาน
```

⚠️ โหมด "ก่อน" ต้อง**ไม่บอกให้ AI ใช้ `scope.mjs` หรือ `gate.sh`** ด้วย — ไม่งั้นได้ครึ่ง ๆ กลาง ๆ

⚠️ **เช็ค `status` ก่อนเริ่มงานทุกครั้ง** — ถ้าเผลอวัดโหมดผิดโดยไม่รู้ตัว ตัวเลขทั้งชุดใช้ไม่ได้
และจะไม่มีทางรู้ย้อนหลังว่ารอบไหนผิด

---

## ⚠️ กติกาเลือกงาน — ข้อนี้ทำให้ตัวเลขเถียงไม่ได้

**ห้ามใช้งานที่เคยวิเคราะห์ไปแล้วในบทสนทนา**

ตัวอย่างที่ห้ามใช้: งานเปลี่ยนฟอนต์ไป `next/font/google` — เรารู้สาเหตุ รู้ไฟล์ รู้วิธีแก้ครบแล้ว
ถ้าเอามาวัด **โดยเฉพาะโหมด "ก่อน"** คำตอบมีอยู่แล้ว → ตัวเลขไม่สะท้อนงานจริง

(แก้ฟอนต์ได้เลยถ้าอยากปิด flaky ถาวร แต่**อย่านับเป็น 1 ใน 5 งานที่วัด**)

**เลือกงานที่ยังไม่เคยคุยกันมาวัดแทน**

## ตารางบันทึก

| งาน | โหมด | ชนิดงาน | โทเคน | เวลา (นาที) | ผ่าน gate รอบแรก | รอบแก้ซ้ำ | หมายเหตุ |
|-----|------|---------|-------|------|:---:|:---:|------|
|     | ก่อน |         |       |      |  —  |     |      |
|     | หลัง |         |       |      |     |     |      |
|     | หลัง |         |       |      |     |     |      |
|     | ก่อน |         |       |      |  —  |     |      |
|     | หลัง |         |       |      |     |     |      |

**นิยาม "รอบแก้ซ้ำ"** = จำนวนครั้งที่ต้องบอก AI ให้แก้ใหม่เพราะผลยังไม่ถูก
นับตั้งแต่ครั้งที่ 2 เป็นต้นไป (ครั้งแรกคือการสั่งงาน ไม่นับ)

> คอลัมน์นี้สำคัญพอ ๆ กับโทเคน — **ครึ่งหนึ่งของการประหยัดมาจาก "ไม่ต้องวนแก้"**
> ไม่ใช่แค่โทเคนต่อรอบที่ถูกลง

**ชนิดงานที่ควรมี** — เลือกจากงานจริง ไม่ใช่งานสมมติ

- แก้บั๊กเล็ก แตะไฟล์เดียว
- **แก้ที่กระทบหลายไฟล์** ← จุดที่มาตรฐานควรได้เปรียบชัดสุด ต้องมีอย่างน้อย 1
- เพิ่มฟีเจอร์เล็ก

---

## ⚠️ ตั้งความคาดหวังให้ถูก ก่อนเห็นตัวเลข

**"ก่อน" ไม่ได้แปลว่า AI โง่** — AI สมัยนี้ค้นหาแบบเจาะจงเป็นอยู่แล้ว ไม่ได้อ่านทั้งโปรเจกต์เสมอไป

| ชนิดงาน | คาดว่าจะเห็นส่วนต่าง |
|---|---|
| งานเล็ก แตะไฟล์เดียว | **น้อย** — AI ปกติก็หาเจอเร็วอยู่แล้ว |
| **งานหลายไฟล์ / โค้ดพันกัน** | **มากสุด** ← ตรงนี้คือที่ที่ "อ่านทั้งโปรเจกต์เพื่อความปลอดภัย" เปลืองที่สุด |

**อย่าผิดหวังถ้างานเล็กได้เลขน้อย** — ให้ดูงานหลายไฟล์เป็นตัวชี้

## ⚠️ n = 5 บอกทิศทางได้ ไม่ใช่เลขแม่น

แต่ละงานขนาดต่างกัน โทเคนเหวี่ยงเยอะ เพราะฉะนั้น:

- **ดูผลรายงานทีละงาน ไม่ใช่ดูแค่ค่าเฉลี่ย** — จะได้เห็นว่าแพทเทิร์นสม่ำเสมอไหม
  (ถ้า 4 งานลด 1 งานเพิ่ม ต้องรู้ว่างานไหนและทำไม ไม่ใช่กลบด้วยค่าเฉลี่ย)
- **เลือกงานก่อน/หลังให้ขนาดใกล้กัน** เท่าที่ทำได้
- **คอลัมน์ "รอบแก้ซ้ำ" อาจชี้ผลชัดกว่าโทเคนดิบ** — gate จับพังเร็ว = ไม่ต้องวนแก้
  ซึ่งเป็นการประหยัดที่ตัวเลขโทเคนต่อรอบมองไม่เห็น

## ⚠️ ข้อจำกัด — เขียนไว้ก่อนใครเอาตัวเลขไปอ้าง

- **macca ไม่มีผู้ใช้จริง ไม่มีเดิมพัน**
  → ตารางนี้วัด **"โทเคน/เวลาต่องาน" (R1) ได้จริง**
  → แต่วัด **"ความกลัวลดลง" ไม่ได้** ซึ่งคือตัวเผาโทเคนที่ใหญ่ที่สุดตามที่วิเคราะห์ไว้
  → **ตัวเลขที่ได้จึงเป็นขอบล่าง** ของประโยชน์จริงบนระบบที่ส่งมอบแล้ว

- **n = 5 น้อยมาก** บอกทิศทางได้ ยังไม่พอสรุปเป็นตัวเลขแม่นยำ

- **ยังไม่มีครึ่ง DB** (typed client, RLS smoke) ซึ่งประเมินว่าแก้ R2 ได้ 70–85%
  → วัดได้แค่ประสิทธิผลของครึ่งเดียว

- ผลขึ้นกับว่า AI ทำตาม `CLAUDE.md` แค่ไหน ซึ่งต่างกันได้ตามรุ่น/การตั้งค่า
  → **จดรุ่นโมเดลไว้ด้วย** และต้องเหมือนกันทั้ง 5 รอบ

**ห้ามเอาตัวเลขจากที่นี่ไปสรุปแทนโปรเจกต์ที่มีลูกค้าใช้จริง** อันนั้นต้องวัดบนโปรเจกต์นั้นเอง
