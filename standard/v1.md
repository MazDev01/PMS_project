# มาตรฐานการทำงานกับ AI — v1

> **สถานะ:** ครึ่งที่ไม่ต้องใช้ DB ทำเสร็จและทดสอบแล้วบน pms-app (2026-08-13)
> ครึ่ง DB ยังทำไม่ได้ เพราะโปรเจกต์นี้ยังไม่มีฐานข้อมูล

## ปัญหาที่มาตรฐานนี้แก้

ทีม dev ไม่กล้าแตะโค้ดที่ AI เขียน เพราะกลัวลามไปส่วนที่ไม่ได้ตั้งใจแก้
พอไม่กล้า ก็ให้ AI นั่งวิเคราะห์ผลกระทบทั้งโปรเจกต์ก่อนทุกครั้ง — ซึ่งคือตัวเผาโทเคนตัวจริง

**หลักการ:** แทนที่จะให้ AI คิดเพื่อความปลอดภัย ให้**เครื่องตอบว่ากระทบที่ไหน** แล้วทำให้**ถอยกลับได้**

---

## หลัก 3 ข้อ

1. **gate ต้องตรงกับโหมดพังจริง** — gate ที่ผ่านทั้งที่ของพัง แย่กว่าไม่มี gate เพราะสร้างความมั่นใจปลอม
2. **บังคับด้วยเครื่องให้มากที่สุด** — ทุกข้อที่พึ่งความมีวินัยจะสลายภายในสองสัปดาห์
3. **วัดผลตัวเอง** — มาตรฐานที่ไม่มีตัววัดก็เถียงกันไม่จบว่าคุ้มไหม

---

## เส้นแบ่งชั้น — ตัวเลขเป็นคนตัดสิน ไม่ใช่ความรู้สึก

เกณฑ์: **ออฟไลน์ได้ + ไม่ต้องใช้ secret** → hook ในเครื่อง · นอกนั้น → CI

| เครื่องมือ | วัดจริงบน pms-app | อยู่ชั้น |
|---|---|---|
| `./gate.sh` (tsc) | **12–16 วิ** | **pre-push** |
| lint ratchet | 57 วิ | CI |
| `next build` | ~110 วิ | CI |
| render smoke | ยิงใส่ production build — server ขึ้นใน 7 วิ | CI |
| `scope.mjs` | ~20 วิ | **ไม่ใช่ gate** — รันก่อนเริ่มงาน |
| **`./gate.sh --full` รวม** | **456 วิ (~7.6 นาที)** | ~250 รอบ/เดือนในโควตาฟรี |

### กฎ: smoke ต้องยิงใส่สิ่งที่จะ deploy จริง

`gate.sh --full` สั่ง `next build` แล้วต่อด้วย `smoke.mjs --prod` ซึ่งเปิด `next start`
**ห้ามปล่อยให้ smoke เปิด `next dev` เอง** ไม่งั้น build ที่เพิ่งทำจะถูกโยนทิ้ง แล้ว CI จะเขียว
โดยไม่เคยแตะของที่ ship จริงเลย

ผลพลอยได้: production build เสิร์ฟทันที server ขึ้นใน **7 วิ** เทียบกับ dev **110 วิ**
และ timeout ปลอมจาก dev ที่คอมไพล์ทีละ route หายไปตั้งแต่ต้นทาง — warm-up เป็นแค่ตาข่ายสำรองของโหมด dev เท่านั้น

**งบเวลาผูกกับความถี่ ไม่ใช่ตัวเลขตายตัว**

hook ข้ามได้ด้วย `--no-verify` เสมอ สิ่งเดียวที่กันคนข้ามคือ**ความน่ารำคาญที่ต่ำพอ**
ซึ่งขึ้นกับว่ามันรันบ่อยแค่ไหน:

| hook | ความถี่ | งบที่รับได้ |
|---|---|---|
| pre-commit | วันละหลายสิบครั้ง | ~15 วิ |
| **pre-push** | วันละไม่กี่ครั้ง | **15–20 วิ สบาย ๆ** |

`./gate.sh` วัดได้ 12–16 วิ ซึ่งชนงบของ pre-commit แต่อยู่ในงบของ pre-push สบาย
เราจึง**ย้าย gate ไป `pre-push`** แทนการลดความครอบคลุมของ tsc

ทางเลือกที่เคยพิจารณาแล้ว**ไม่เลือก:** ตัด `.next/types/**` ออกจาก program ให้ tsc เร็วขึ้น
— เป็นการซื้อความเร็วด้วยการทิ้งการตรวจ type ของ route params ซึ่งขัดหลักข้อ 1 โดยตรง

การย้ายไป pre-push ได้ทั้งสองอย่าง: tsc เต็มรูปแบบ **และ** ยังจับก่อนโค้ดออกจากเครื่อง

(เลข 26–29 วิที่เคยเห็นคือตอนเครื่องยุ่งจากการ commit ไฟล์จำนวนมาก ไม่ใช่ steady state — ไม่ไล่ต่อ)

### tsc ช้าเพราะอะไร — ตรวจแล้ว ไม่ใช่เดา

เคยเขียนไว้ว่า "`next build` ล้าง incremental cache ของ tsc" — **ตรวจแล้วพบว่าผิด** ลบทิ้ง

หลักฐานจาก `--extendedDiagnostics` (2026-08-13):

| | warm ไม่มีไฟล์เปลี่ยน | ทันทีหลัง build | แก้ leaf file | แก้ `lib/data.ts` |
|---|---|---|---|---|
| Files | 610 | 610 | 610 | 610 |
| Instantiations | 0 | 0 | 5,624 | 161 |
| Check time | ไม่มี (ข้าม) | ไม่มี (ข้าม) | 0.53s | 0.53s |
| **Total** | 12.71s | **6.85s** | 6.30s | 12.69s |

- `sha256` ของ `tsconfig.tsbuildinfo` **เหมือนกันเป๊ะก่อน/หลัง `next build`** → build ไม่แตะ cache
- `next-env.d.ts` ทั้ง mtime และ hash **ไม่เปลี่ยน** → ไม่ใช่เหตุเช่นกัน
- ลอง reproduce: build แล้ว gate ทันที = **9.25 วิ** ไม่ใช่ 25 วิ → ตัวเลขเดิมคือ noise จากเครื่องที่เพิ่งรัน build+smoke เสร็จ

**คำอธิบายที่ถูก:** เวลาส่วนใหญ่ไม่ได้อยู่ที่การตรวจ type (`Check time` แค่ 0.53 วิ)
แต่อยู่ที่ **parse + I/O ของ 610 ไฟล์ / ~200,000 บรรทัด `.d.ts`** ซึ่งผันผวนตาม disk cache ของ OS
ผันผวนแบบนี้ไม่ว่าจะแก้ไฟล์อะไรหรือไม่แก้เลย

**บทเรียนวิธีวัด 2 — จับเวลาทั้งคำสั่ง ไม่ใช่เลขที่เครื่องมือรายงานเอง**

| | เวลา |
|---|---|
| `./gate.sh` steady state 3 รอบติด | 12.4 / 13.7 / 15.6 วิ |
| ตัวเลขที่ tsc รายงานเอง (`Total time`) | 7.3 วิ |

ส่วนต่าง ~5–8 วิคือ node startup + bash + เปิด process ซึ่ง `--extendedDiagnostics` ไม่นับให้
ถ้าเชื่อเลขของ tsc จะได้ตัวเลขที่ดูดีกว่าความจริงเท่าตัว — ผู้ใช้รอทั้งคำสั่ง ไม่ได้รอแค่ tsc

**บทเรียนวิธีวัด 1 —** ตัวเลข "warm 5 วิ" ที่วัดตอนแรกมาจากการรัน tsc บนโค้ดที่ไม่มีอะไรเปลี่ยน
ซึ่ง `Instantiations: 0` บอกว่า tsc **ข้ามการตรวจทั้งหมด** — เป็นสถานการณ์ที่ไม่มีวันเกิดตอน commit จริง
เวลาวัด gate ต้องวัดตอนมีไฟล์เปลี่ยน ไม่งั้นได้เลขที่สวยเกินจริง

ผลที่ต้องยอมรับตรง ๆ: ของที่ทรงพลังที่สุดไปอยู่ CI หมด แปลว่า pre-commit ที่ "ฟรีไม่จำกัด"
ครอบแค่ type error ส่วนตัวจับจอขาวกินโควตา CI จริง — ยังจ่ายไหวเพราะรันตอน push ไม่ใช่ทุก commit

## blast radius — สองกลไก ไม่ใช่หนึ่ง

| อยากรู้อะไร | เครื่องมือ | สถานะ |
|---|---|---|
| ใครเรียก symbol นี้ | `scope.mjs` (TS language service) | ✅ ใช้ได้ |
| ใครใช้คอลัมน์/ตารางนี้ | regenerate types + `tsc` | ⏸ รอ DB |

**เงื่อนไขของกลไกที่สอง:** ต้องผูก `createClient<Database>` เท่านั้น
ถ้าเรียก `.select('customer_name')` เป็น string โดยไม่ผูก generic → `tsc` มองไม่เห็น → blast radius ฝั่ง DB เป็นศูนย์
นี่เป็น**งานเตรียมที่ต้องทำ ไม่ใช่ของที่ได้มาฟรี** และต้อง gate ตัวมันเองไม่ให้เสื่อม (ดู ratchet)

**สิ่งที่ scope.mjs มองไม่เห็น** (พิมพ์เตือนไว้ใน output ทุกครั้ง เพราะ false confidence เกิดตอนคนอ่านผล ไม่ใช่ตอนอ่านคู่มือ):
- logic เดียวกันที่ถูกเขียนซ้ำ — สำเนาไม่ใช่ reference
- string key — `.rpc()`, flag, event, route
- coupling ข้ามขอบเขต — DB trigger, external API, service อื่น

สองแบบแรกยังต้องคนดู · แบบที่สาม**ไม่ต้องรอคนตลอดไป** — ย้ายเข้าระบบ type ไม่ได้เพราะปลายทางอยู่นอกโปรแกรม
แต่พิสูจน์ได้ด้วย **seam test** ซึ่งคือ characterization test ที่วางไว้ที่รอยต่อ (RLS smoke คือกรณีหนึ่งของมัน)

```
coupling อยู่ในโปรแกรม มี type  →  static analysis
coupling ข้ามขอบเขต             →  seam test
```

## ครึ่งที่ยังขาด — ปลดล็อกเมื่อมี DB

- `supabase gen types typescript` + `git diff --exit-code` = type drift (CI เท่านั้น ต้องใช้ token + เน็ต)
- ผูก `createClient<Database>` ให้ครบ + เปิด `@typescript-eslint/no-unsafe-member-access` ใน ratchet (CI เท่านั้น เพราะ type-aware lint ช้า)
- RLS smoke — **anon key + JWT ของ test user จริง ห้ามใช้ service_role**
  service_role ข้าม RLS ทั้งหมด จะได้แถวเสมอ = ปิดบังบั๊กตัวที่ตั้งใจจะจับพอดี
  ต้อง assert สองทิศ: เห็นของตัวเอง (>0) **และ** ไม่เห็นของ tenant อื่น
  (RLS พังแบบเห็นมากไป = ข้อมูลรั่ว ซึ่งอันตรายกว่า และ `>0` จับไม่ได้)
- migration linter — บล็อก `DROP COLUMN` / `RENAME` / `ALTER TYPE` เว้นแต่มี `-- reviewed: <เหตุผล>`

## ของที่เลื่อนไว้ — เงื่อนไขปลดล็อกต้องนับได้

เลื่อนเพราะ**ยังไม่มีหลักฐานว่าจำเป็น** ไม่ใช่เพราะไม่ดี ทุกอันมีที่จดใน [gaps.md](gaps.md) เพื่อให้หลักฐานสะสมได้จริง

| ของ | ปลดล็อกเมื่อ | ทำไมเลื่อนได้ |
|---|---|---|
| clone detector | `dup` ใน gaps ถึง 2 | jscpd จับได้แค่ Type 1/2 · AI มัก**เขียนใหม่**ไม่ได้ก๊อป → Type 3/4 ซึ่งจับไม่ได้ ยกพื้นขึ้นเฉย ๆ ไม่ได้ปิดช่อง |
| const registry + rpc lint | `string-key` ใน gaps ถึง 1 | dev ทุกคนต้องจำธรรมเนียมใหม่ = ต้นทุน adoption แพงสุด |
| contract รอยต่อโมดูล (R4) | v1 พิสูจน์แล้ว **และ** มี `seam` ใน gaps ≥1 | ไม่งั้นจะไปแก้ปัญหาที่ยังไม่รู้ว่ามีจริง |

**เกณฑ์ตัดสินว่าอะไรเลื่อนได้:** incident ที่เรียนรู้จากมันได้ (ราคาถูก เจอในทีม) → รอให้พังก่อนได้ ·
incident ที่เรียนรู้จากมันไม่ได้ (แพง เจอหน้าลูกค้า) → ต้องป้องกันล่วงหน้า

### perf ไม่เข้าเกณฑ์นี้ — ต้องป้องกันล่วงหน้า

โหมดพังของ perf คือ "ล่มตอนคนเยอะ" ซึ่งเกิดต่อหน้าลูกค้า ถ้ารอให้พังก่อน = ลูกค้าเจอก่อนเราทุกครั้ง

> **โปรเจกต์ที่จะมีผู้ใช้จริง ก่อนส่งมอบต้องระบุสองตัวเลขแล้ววัดหนึ่งครั้ง**
> - **ปริมาณข้อมูล** — seed เท่าที่คาดว่าจะมีใน 12 เดือน แล้ววัดเวลาโหลด 3 หน้าที่ใช้บ่อยสุด
> - **จำนวนคนพร้อมกัน** — ยิงพร้อมกันเท่าผู้ใช้สูงสุดที่คาดไว้

แยกสองตัวเพราะเป็นคนละโหมดพัง — seed เยอะจับ query ช้า/ไม่มี index
แต่**จับ "เกิน N คนล่ม" ไม่ได้** อันนั้นเป็นเรื่อง connection pool / concurrency ต้องยิงพร้อมกันถึงเห็น

ยังไม่ต้องอัตโนมัติ วัดด้วยมือครั้งเดียวก่อนส่งมอบก็พอ

## นิยาม "v1 พิสูจน์แล้ว"

วัดบนโปรเจกต์ที่**ส่งมอบจริง** 1 ตัว สองรอบห่างกัน ≥2 สัปดาห์ แล้วได้ทั้งสองข้อ:

- โทเคนต่องานแก้ **ลดลง ≥25%**
- งานที่ผ่าน gate รอบแรก **≥70%**

กติกาจดตัวเลข: **1 เซสชัน = 1 งาน** แล้วจด `/cost` ตอนจบ ถ้าไม่มีกติกานี้ ตัวเลขจะเทียบกันไม่ได้

⚠️ สองตัวเลขนี้ตั้งจากการประมาณ ยังไม่มีข้อมูลรองรับ — **ให้ทบทวนหลังได้ baseline รอบแรก**

---

## เดโมพิสูจน์อะไรไม่ได้

pms-app ไม่มีผู้ใช้จริง ไม่มีเดิมพัน เพราะฉะนั้น:

- **ตัวเลข baseline จากเดโมเทียบกับโปรเจกต์จริงไม่ได้** ห้ามเอาไปอ้างว่ามาตรฐานได้ผล
- **"ความกลัวลดลงจริงไหม" พิสูจน์ไม่ได้** เพราะไม่มีอะไรให้กลัว

เดโมพิสูจน์ได้แค่ว่า**กลไกทำงาน** — ซึ่งก็มีค่าพอ เพราะทำให้ตอนโปรเจกต์จริงมา เราก๊อปของที่ใช้ได้แล้วไปใช้ ไม่ต้องออกแบบใหม่

## ประเมินว่าแก้ปัญหาได้เท่าไหร่

ตัวเลขจากการให้เหตุผล ยังไม่ได้วัด:

| ปัญหา | แก้ได้ราว | เพดานติดตรงไหน |
|---|---|---|
| front-back ต่อไม่ติด (R2) | 70–85% | type ตรงแต่ความหมายผิด |
| กลัวแตะโค้ด AI | 60–75% | ความเชื่อมั่นต้องใช้เวลา |
| พังในสภาพจริง (R3) | 50–65% | ไม่มี gate ด้าน perf/concurrency |
| โทเคนเยอะ (R1) | 40–55% | งานที่จำเป็นจริง + บทสนทนา กดไม่ลง |
| กระจายงาน AI (R4) | 30–45% | ยังไม่มี contract ที่รอยต่อโมดูล |
